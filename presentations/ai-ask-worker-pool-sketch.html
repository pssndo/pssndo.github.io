Emperor Data-Research Worker Pool

Architecture sketch for exposing Claude + readonly-db MCP + the docs/overview knowledge base as a service OpenClaw can call.

Goal. OpenClaw posts an ask. A pool of Claude Code workers picks it up, researches against MySQL and ClickHouse (read-only), writes a markdown answer, and OpenClaw fetches the result.

Everything inside the dashed box runs in one container. The only ingress is port 8080 for OpenClaw. The only egress is SELECT traffic to the two databases through readonly-db-mcp.

Ask lifecycle

sequenceDiagram
  autonumber
  participant OC as OpenClaw
  participant API as ask-api (SQLite)
  participant W as worker wN (tmux)
  participant CL as claude -p
  participant DB as readonly-db-mcp → MySQL / ClickHouse

  OC->>API: POST /asks {question, requester, callback_url}
  API-->>OC: {id, status: pending}
  loop every 30s, 5 workers
    W->>API: POST /asks/next {worker}
    API-->>W: ask (atomic UPDATE → processing) or 204
  end
  W->>CL: claude -p question --append-system-prompt-file bootstrap.md --allowedTools mcp__readonly-db__*
  CL->>CL: read docs/overview (schema, playbook, gotchas)
  CL->>DB: query_clickhouse / query_mysql (SELECT only, ≤30s each)
  DB-->>CL: markdown table (≤1000 rows)
  CL-->>W: {result: answer_md}
  W->>API: PUT /asks/{id} {status: done, answer_md}
  API-->>OC: callback_url (or OC polls GET /asks/{id})
  OC->>API: DELETE /asks/{id}

Typical wall time is 1 to 6 minutes per ask. A 15-minute timeout around the claude call and a stale-lock sweeper on the API cover worker crashes.

Queue state machine

stateDiagram-v2
  [*] --> pending : POST /asks
  pending --> processing : POST /asks/next (atomic claim)
  processing --> done : PUT status=done
  processing --> failed : PUT status=failed / timeout 900s
  processing --> pending : stale > N min (sweeper)
  done --> [*] : DELETE /asks/{id}
  failed --> [*] : DELETE /asks/{id}

Knowledge base mounted into every ask: docs/overview/SCHEMA_MACHINE_READABLE.yaml, CROSS_DB_ANALYSIS_PLAYBOOK.md, DATA_MODEL_REFERENCE.md, SENDOUT_IDENTIFIER_MITIGATION.md, HOW_AD_SELECTION_WORKS.md, EMPEROR_SYSTEM_OVERVIEW.md, plus AI_DATA_RESEARCH_BOOTSTRAP.md as the system prompt (query discipline, GDPR views, fraud and device semantics).

1. ask-api (the queue) — about 80 lines of FastAPI + SQLite

MethodPathWhoEffect
POST/asksOpenClaw{question, requester, callback_url?} → {id, status: pending}
GET/asks/{id}OpenClawstatus + answer_md when done
POST/asks/nextworkeratomic claim: UPDATE … SET status='processing', worker=? WHERE id=(SELECT id … pending LIMIT 1); returns the ask or 204
PUT/asks/{id}worker{status: done|failed, answer_md, artifacts[]}; fires callback_url if set
DELETE/asks/{id}worker / OpenClawremove from queue after the result is collected
  • Atomic claim in the DB replaces "first tmux marks it". Five pollers cannot double-claim a row.
  • Stale-lock sweep: processing rows older than N minutes go back to pending (worker died).

2. Worker loop (one per tmux window, 5 windows)

# worker.sh  — runs inside tmux window wN
while true; do
  ask=$(curl -sf -X POST localhost:8080/asks/next -d "{\"worker\":\"$W\"}") || { sleep 30; continue; }
  id=$(jq -r .id <<<"$ask"); q=$(jq -r .question <<<"$ask")
  out=$(timeout 900 claude -p "$q" \
        --append-system-prompt-file docs/AI_DATA_RESEARCH_BOOTSTRAP.md \
        --allowedTools "mcp__readonly-db__*,Read,Grep,Glob,Bash(python3 *),Bash(jq *)" \
        --max-turns 60 --output-format json 2>/tmp/$id.err) \
    && curl -s -X PUT localhost:8080/asks/$id \
         -d "$(jq -n --arg a "$(jq -r .result <<<"$out")" '{status:"done",answer_md:$a}')" \
    || curl -s -X PUT localhost:8080/asks/$id \
         -d "{\"status\":\"failed\",\"answer_md\":\"$(head -c 2000 /tmp/$id.err)\"}"
  sleep 30
done
  • claude -p is headless. No skip-permissions flag is needed because --allowedTools is an explicit allowlist: MCP read tools, repo reads, and python/jq for parsing result dumps.
  • Each run is a fresh context, so there is no cross-ask leakage. Docs are re-read per ask (cheap, prompt-cached).
  • Deliverables land in tmp/<ask-id>/ per the bootstrap doc; answer_md is the report.

3. Container (one Dockerfile, derived from claude-sandbox)

FROM claude-sandbox                    # node:20-bookworm + tmux + python3 + claude CLI
RUN pip install readonly-db-mcp fastapi uvicorn
COPY ask_api.py worker.sh supervisor.sh /app/
WORKDIR /workspace                     # bind-mount emperor repo (docs/ + .mcp.json)
ENV MYSQL_1_DSN=... CLICKHOUSE_1_DSN=...   # SELECT-only DB users (Layer 3)
CMD ["/app/supervisor.sh"]
# supervisor.sh: uvicorn ask_api:app --port 8080 &
#                tmux new -d -s pool; for i in 1..5: tmux new-window -t pool "W=w$i /app/worker.sh"
#                tmux attach   (or `tail -f` for detached mode)

Mounts: emperor/:/workspace:ro (docs + .mcp.json), a named volume for ~/.claude (OAuth / API key), and an ask.db volume for the queue. Port 8080 is exposed to OpenClaw only (LAN or docker network).

4. OpenClaw integration contract

OpenClaw skill/tool "emperor_research":
  1. POST http://pool:8080/asks {question, requester:"<slack user>", callback_url:"<openclaw hook>"}
  2. either wait for the callback, or poll GET /asks/{id} every 15s until status ∈ {done, failed}
  3. render answer_md to the user; DELETE /asks/{id}

Typical latency: 1–6 min (ClickHouse 30s/query cap × several queries + reasoning).
Concurrency: 5 asks in flight; queue depth unbounded (SQLite).

5. Guardrails in place, and to add

  • Read-only is enforced three times by readonly-db-mcp: SQL AST validation, read-only transaction, SELECT-only DB user. No ask can write.
  • GDPR: userIdentity / ipAddress only via the ai_reader_us_clients_* views (bootstrap doc §2). EU clients get segment-level analysis only.
  • To add: per-ask turn cap (--max-turns), 15-minute wall timeout, API-key header on ask-api, SQL logging (readonly-db already logs every query).
  • Optional next step: swap SQLite for Redis/RQ if the pool spans more than one host; add GET /asks?status= for an OpenClaw dashboard.
